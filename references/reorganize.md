# 整理规则

整理过程中写提交说明，按 SKILL.md 的提交规则执行；改动仓库前先确认 SKILL.md「授权边界」。

- 整理范围是当前分支相对上游分支多出来的提交；没有上游分支时，请用户指定范围。
- 工作区有未提交改动时，先停下问用户。
- 遇到无法继续的失败时停下，报告停在哪一步；不把做了一半的结果当成完成。

## 一、硬约束

1. 只重写历史，不改代码：整理后分支最后一个提交的 tree hash，必须和开始时记下的原分支提交的 tree hash 相同。两者都用 `git rev-parse <提交>^{tree}` 取得。
2. 每个提交都能单独检出：逐个提交运行静态检查，全部通过；需要连接外部资源的测试不运行。静态检查用项目已有的 lint、类型检查或编译命令，找不到时问用户。
3. 整理时原分支不动，结果放在新分支上，不合并到其他分支，也不推送；开始时记下原分支最后一个提交的 hash，作为核对终态的基准。
4. 历史是一条直线：没有合并提交，没有重复的标题。
5. 不能把最终状态直接覆盖上去来凑零差异。出现差异时，要查清是删错了还是漏了，补成新提交，或者修正对应的提交。

## 二、范围

每个提交都要检查：确实是原子提交的，内容不动；不是的，就拆开、合并或调整顺序。

## 三、并回原提交还是单独成提交

### 并回原提交

- 修补：修的是某个提交引入的缺陷，并回那个提交。
- 改口径：把某个提交定下的规则改成另一条，并回定规则的那个提交，直接写成最终状态。
- 改了又改回、加上又原样删掉的：两边一起删除，不保留。
- 删除没用到的导出、没人读的字段、重复代码内容的注释，以及合并重复逻辑：并回引入它们的提交。
- 同一处改了两次：只保留最后一次的结果。

在整理范围内反复修改的内容，只保留最终状态。新历史里的每个提交，都应该像是一开始就这么写的。

### 单独成提交

- 新能力：原提交时还不存在的输出、动作、入口、接口，按它自己的最终状态写。
- 跨模块的统一政策：各处改法机械一致的，合成一个提交；各处各有判断的，每处一个提交。
- 共享函数、约定文档、测试设施：见 SKILL.md「二、什么单独成提交」。用到它们的代码，直接按使用它们的写法写，不再单独出现「改用」提交。

拿不准时，从最终状态倒推。

## 四、顺序

- 按依赖关系排序，不按时间排序：约定 → 共享函数 → 核心 → 服务 → 各模块 → 跨模块政策 → 各模块的后续决定。
- 被依赖的提交排在依赖它的提交前面。
- 同一模块的改动尽量排在一起；不同模块之间不交叉，同一模块内部可以调整顺序。
- 正文里描述的问题，必须在父提交中真实存在。

## 五、流程

1. 逐个检查来源提交，确定每个 hunk 的去向：并回哪个提交、单独成为哪个提交，或者丢弃。
2. 从分叉点开始逐个生成提交，每生成一个就运行一次静态检查。检查失败就当场修复，不带着失败往下做。
3. 校验：硬约束全部成立；先加后删、净变化为零的内容行应该为零，剩下的逐条说明原因；说明里没有编号和 hash。

## 大规模整理

用户说明这次是大规模整理时，读 `large-scale.md`。如果提交多到一次看不完、需要分段处理，先问用户要不要启用。
