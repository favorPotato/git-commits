# 批量改写提交说明

只改说明，不改内容。改写说明按 SKILL.md 的提交规则执行；改动仓库前先确认 SKILL.md「授权边界」。

## 一、硬约束

1. 每个提交的 tree 不变，提交数不变，顺序不变。
2. 原分支不动，结果放在新分支上，不合并到其他分支，也不推送。
3. 保留作者和作者日期。用 `git commit-tree` 按原顺序逐个重建提交；不用交互式 rebase，它默认会丢掉空提交和与上游补丁相同的提交。

## 二、改写口径

- 默认保留原说明，只改违反规则的地方。每处改动都写明违反了哪一条。
- 改写后的标题更难读、更抽象，或者丢了信息时，保留原标题。
- 每条都重新判断 type 和作用域，不只改标题的文字。
- 原因只取自事先抽好的出处，没有出处就留空。原正文按 SKILL.md 的正文规则判断去留。

## 三、分工

- type、作用域名称、原因出处这类需要全局判断的事，先在主对话里定死，再分批交给子代理。子代理只负责照着套用。
- 给子代理的提示只引用 SKILL.md 的规则，不另加更严的口径。
- 子代理只看到自己那一段，它提出的「这条该并进另一条」「这里该拆」不可信，由主对话汇总后再定。

## 四、复核

用脚本列出新旧说明的全部差异，逐条检查：

- 同一类改动在各批之间口径是否一致；
- 正文有没有重复标题，包括同义改写；
- 改后的标题有没有比原标题更差。

不靠口头确认「已经改回去了」，也不靠「新正文是否包含旧标题片段」这类文字匹配，它漏过同义改写。
