# 提交说明正反例

起草或改写提交说明前先读这里。每组先放反例（✗），再放正例（✓），最后一句点明差别。例子改编自同一个项目的真实提交：项目名词换成了通用说法，正反例之间的差别和用户原话保持原样。

来源标记：
- 〔纠正〕：用户否掉初稿后定下的说明
- 〔认可〕：用户直接认可的说明
- 〔亲改〕：用户自己改定的说明
- 〔改坏〕：模型照规则批量改写时改差的说明

## 1. 看得懂：不看 diff 的人能说出改了什么

✗ docs(spec): deleted 暂定按表结构文档自动推导
✓ docs(spec): 一轮同步中未见的记录暂定标为 deleted
〔纠正〕用户的反应是「鬼知道是啥」，改完后说「这样我就看得懂了」。

✗ docs(spec): 拓扑暂定服务写运行库全表
✓ docs(spec): 拓扑暂定先写运行库再推云端
〔纠正〕用户原话：「看不懂」。原标题写的是机制，改后写的是读者关心的结果。

## 2. 写意图层面的结果，不写机制

✗ docs(spec): 推云端暂定订单和用户原样含错误字段
✓ docs(spec): 推云端带上同步错误记录
〔纠正〕「原样含」描述的是怎么推，读者要知道的是推了什么。

✗ docs: README 移除新服务上线门槛
✓ docs: README 不提及内部调研仓库
〔纠正〕diff 表面上删了一段，实际意图是不让本仓库提到另一个仓库。用户原话：「他不是移除门槛，而是改了措辞」。

## 3. 具体的结果值要写

✗ fix(browser): 空闲浏览器上下文延长默认保留时间
✓ fix(browser): 空闲浏览器上下文默认保留 900 秒
〔改坏〕900 秒是改动的结果，不是实现细节，删掉之后标题就不知道改成了多少。

✓ docs(spec): 新建脚手架、建表验证与类型定义首版

✗ docs(db): 原始号码由 phone_raw 承载，区号与分机取自 contact
✓ docs(db): 恢复 phone_raw 列
〔纠正〕这一列以前删过，这次是加回来，所以写「恢复」。用户原话：「恢复原来的口径……你帮我组织语言」。

✗ docs(spec): 表结构改为以 db 文档为准
✓ docs(spec): 补写表结构以 db 文档为准
〔纠正〕口径一直如此，只是之前漏写了，所以写「补」，不写「改为」。

✓ docs(spec): 新建脚手架、建表验证与类型定义首版
〔纠正〕「story 1」是规划阶段的编号，读者不知道它指什么。用户原话：「不要代号」。

   data-model.md 已拆走。路径写到 order.md / runtime.md；当代号仍称 docs/db。
✓ docs(spec): 引用从 data-model.md 改到 docs/db

## 6. 「与」、顿号、逗号是提醒检查的信号，本身不算违规

连接同一个动作的几个宾语，保留：

✓ docs(spec): 移除待办清单中的过期与无效条目
✓ docs(db): 数据模型拆为业务与运行两份
✓ test: 移除旧版对照、模拟登录与旧集成测试
✗ test: 移除旧版对照、模拟登录、旧集成测试
〔认可 / 改坏〕最后一条只是把「与」换成顿号，形式上避开了禁令，内容一点没变。

后半句是同一个决定的条件、范围、例外或后果，保留：

✓ docs(db): 约定各层 phone_raw 多个号码以逗号分隔，phone 取第一个
✓ fix(scraper): 详情页或促销页缺少数据时，门店上下文丢失判为掉线
✓ docs(db): 其余价格增加非主价档的限时折扣价，并计入促销价
✗ docs(db): 其余价格增加计入促销价的非主价档限时折扣价
〔认可 / 改坏〕为了去掉「并」，把修饰语堆在一起，读起来更费劲。

✓ fix(clean): 重量和体积按整串匹配，并按原文单位换算
✗ fix(clean): 重量和体积只按整串数值和其中的单位换算
〔改坏〕改写后意思变了。

✓ feat(browser): 登录提交优先回车，没有请求且原页未动才点按钮
✗ feat(browser): 登录提交优先回车
   页面跳转慢的网站不应在按键处因等待超时失败；没有请求且原页未动才点按钮。
〔改坏〕把条件从标题挪进正文，标题就不完整了，正文也混进了不是原因的内容。

两个能各自单独回退的决定，才要处理：

✗ docs(spec): 任务派发改走命令行，状态流转改由队列强制
✓ docs(spec): 控制入口定为命令行
〔纠正〕状态流转交给队列是命令行入口的派生改动，所以用一个结果覆盖。如果它是独立的决定，就该拆成两个提交。

## 10. 正文写原因，不重复标题

✓ fix(scraper): 详情页或促销页缺少数据时，门店上下文丢失判为掉线
   登录一段时间后门店上下文会丢，页面仍返回成功；促销页显示零条时和确实没有促销无法区分。
✓ fix(db): 空闲数据库连接出错时只记日志
   这个错误发到连接池上，没有监听就是未捕获异常，常驻进程会退出。
✓ fix(clean): 含字母的条码照原文保存，不再切成纯数字
   - 抽出数字或按位数切开都会得到来源没给过的码。
   - 科学计数法含有字母，但不是条码，存空。
〔认可〕最后一例用列表，是因为两条都是这个决定的约束，而且都是标题里没有的。

✗ feat(inventory): 按列表徽标刷新库存，没有徽标记为有货
   - 已有行的库存不会在日常刷新里更新。
   - 没有徽标记为有货。
✓ feat(inventory): 按列表徽标刷新库存，没有徽标记为有货
   已有行的库存不会在日常刷新里更新。
〔改坏〕第二条只是抄了一遍标题。

✗ docs(spec): 技术栈表补齐实际依赖，并收回对应的未定选型
   收回对应的未定选型。
✓ docs(spec): 技术栈表补齐实际依赖，并收回对应的未定选型

   各数据源的更新策略已在代码和规划里定下，日常刷新的列范围以 db 文档为准。

## 11. 切分

✗ docs(db): 订单表补优惠标记与库内列注释（正文里还写了删掉三列）
✓ docs(db): 订单表补优惠标记
✓ docs(db): 去掉未实装列 legacy_flag / source_note / total_count
✓ docs(db): 补库内列注释
〔纠正〕删列这件事标题里没有，用户原话：「删列我忘了写进提交信息？」。标题写不下的决定，说明该拆。（第二条的「去掉」按第 8 组应写作「移除」，这里保留原提交的用词。）

✓ docs(db): 数据模型拆为业务与运行两份
〔认可〕diff 看起来是一次重命名加两个新文件，在作者看来只是「拆分＋派生」，所以算一个提交。伴生和派生的判断以作者意图为准。

以下情况算一个决定，不拆：
- 同一个函数里的两个行为，比如「失败重试一次」和「连续出错就停」。
- 顺手改的措辞，比如同一提交里把 `.raw` 写成 `raw`。
- 只为这个提交服务的辅助代码和测试。
- 条码清洗里顺带处理的科学计数法。
